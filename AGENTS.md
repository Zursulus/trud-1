# AGENTS.md

Короткая карта для AI-агентов и разработчиков. Это не журнал проекта и не источник текущего production state.

## Перед изменениями

1. Уточнить конкретную задачу и её source of truth.
2. Проверить `git status --short`, актуальную ветку и HEAD.
3. Прочитать только нужную документацию из карты ниже.
4. Не считать GitHub push равным production deploy.
5. Для production-задач отдельно подтвердить фактически установленный SHA.

## Постоянные ограничения

- Не отлаживать напрямую на production.
- Не выполнять destructive SQL и не обходить модельные проверки прямым SQL / bulk update.
- Не удалять пользователей, роли, права, историю или исходные данные без отдельной подтверждённой задачи.
- Не придумывать отсутствующие участки, даты, показания, платежи или соответствия импорта.
- Не выбрасывать неоднозначные данные: оставлять их на ручную проверку.
- Публичный репозиторий не должен содержать PII, телефоны, банковские данные, секреты, `.env`, private-data или backup.
- Изменения production, миграции, dependencies и security выполняются только как отдельная явная задача с проверкой и планом отката.

## Карта документации

- `README.md` — публичная часть и общий вход.
- `backend/README.md` — модель данных, рабочие функции и безопасные допущения.
- `docs/PLAN.md` — рабочий план и исторические контрольные точки; текущий NOW/NEXT сверять с Linear.
- `docs/ROLES.md` — роли, аудит и рабочее место оператора.
- `docs/MFA.md` — второй фактор и восстановление доступа.
- `ops/DEPLOYMENT.md` — совместимый deploy и rollback.
- `ops/RECOVERY.md` — backup и восстановление.

## Импорт данных

Сохранять происхождение данных: `SOURCE → DERIVED → CORRECTED → IMPORT PACKAGE → DRY RUN → PRODUCTION`.
Новая производная версия не является основанием удалять исходник.

## Проверка результата

- Запускать минимальный релевантный набор тестов, затем расширять при необходимости.
- Для deploy/ops-изменений проверять соответствующие тесты и shell syntax.
- После существенной работы вернуть: что изменено, что проверено, риски, commit/PR и следующий шаг.

Не записывать сюда временные SHA, сегодняшний CI, длинные логи или закрытые баги — это оперативная/историческая информация, а не постоянная инструкция.
