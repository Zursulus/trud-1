# Редактор публичного сайта

Раздел `/work/documents/` теперь называется «Сайт». Новости и документы сохраняют прежние URL, права и проверку отсутствия закрытых данных. Документы жителей остаются в отдельном закрытом блоке этого раздела.

## Работа правления

1. Создать объявление или новость, заполнить текст и сохранить черновик.
2. Открыть «Предпросмотр» сохранённой версии. Карточка новости открывает полный текст по кнопке «Подробнее». Предпросмотр использует те же `app.js`, `style.css` и `public-content.css`, что и главная, и доступен только сотруднику с правом просмотра соответствующего материала. Несохранённые изменения в него не входят.
3. Для публикации отметить проверку отсутствия закрытых данных и нажать «Опубликовать». Для изменения существующей записи нужна причина. Редактор V2 может создавать/редактировать черновики; публикатор V2 меняет статус сохранённого материала без редактирования текста. Политики MFA и maker/checker такие же, как у новостей. Шаблоны редактора, публикатора и администратора V2 обновлены до версии 2. Уже выданные V2-назначения сохраняют прежний снимок прав: новые права выдаются уполномоченным администратором отдельным назначением, без автоматического расширения старого конверта.
4. Поле новости «Опубликовать с даты» задаёт начало показа по местной дате Django. «Закреплено» ставит новость перед обычными, сохраняя сортировку по дате внутри каждой группы.
5. Объявление показывается с начальной по конечную дату включительно; конец можно не задавать. При пересечении периодов сайт выбирает одну запись: наиболее позднее начало, затем наибольший ID. В списке видно, какое объявление заменено другим. Снятие выбранной записи возвращает предыдущее активное объявление, а отсутствие активных возвращает статическое письмо.
6. Кнопка объявления имеет текст и одну цель: опубликованный документ, опубликованная новость или внешний HTTP(S)-адрес. Если связанный материал снят с публикации или его дата ещё не наступила, кнопка скрывается. Ссылки на новости работают и после выхода новости за первые 12 карточек фида.
7. Картинку PNG/JPEG до 5 МБ можно загрузить в форме объявления либо выбрать из уже загруженных картинок. Оригинал не заменяется. SVG/HTML запрещены; расширение проверяется вместе с сигнатурой. Проверка не декодирует растровое изображение. Публичный обработчик отдаёт картинку только выбранного активного объявления с фиксированным image MIME и `nosniff`; каталог media не открывается. В предпросмотре черновая картинка доступна через отдельный защищённый обработчик.
8. «Контакты и приём» — одна запись с почтой, телефоном, адресом, часами и пояснением. Сначала сохранить, проверить предпросмотр, затем опубликовать.

Новые блоки и картинки используют `RecordedModel`: валидация при сохранении, версия против устаревшей формы, simple-history с автором и причиной. Старые новости/документы сохраняют существующий журнал публикаций.

## Совместимость и выпуск

Миграция `public_site.0002` добавляет таблицы новых блоков, картинок и их истории. В существующей таблице новостей меняется только подпись `is_featured`, данные не преобразуются. Seed с реальными контактами не добавляется: в исходном `index.html` этой ветки нет статических контактов/часов. До публикации контактов новый раздел скрыт. Исходное письмо главной оставлено в HTML.

Перед выпуском выполнить штатный precheck и проверенный backup БД и media по `ops/DEPLOYMENT.md` / `ops/RECOVERY.md`. Проверить миграцию на PostgreSQL в тестовом окружении: SQLite не подтверждает поведение блокировок PostgreSQL. Далее применить миграции, выполнить `setup_roles` для синхронизации штатных Django-групп, обновить backend и публичные `index.html`, `app.js`, `public-content.css` согласованным выпуском. Публичная статика и backend имеют отдельные процедуры установки. Эта задача не выполняет deploy.

Старый frontend игнорирует дополнительные поля фида; новый frontend при старом/пустом фиде оставляет статическое письмо. Новые блоки пусты до явного создания/публикации. Предпросмотр требует новой версии публичного `app.js`.

Откат кода: вернуть предыдущие backend и публичные файлы, оставив добавленные таблицы и media на месте — старый код их не использует. Не откатывать миграцию автоматически: обратная миграция удалит созданный контент и историю. Удаление схемы допустимо только отдельной процедурой после сохранения и проверки резервной копии новых данных.

## Проверки

- `manage.py test water config public_site`, `check`, `makemigrations --check --dry-run` в тестовом окружении.
- `node backend/public_site/test_frontend.cjs` — проверка DOM-рендеринга и fallback без браузера и зависимостей.
- Шаг `Validate public homepage invariants` из `.github/workflows/backend.yml`.
- Перед выпуском вручную проверить с правами редактора/публикатора: черновик → предпросмотр → публикация → изменение → снятие; даты, кнопки на документ/новость/внешний адрес, картинку, контакты, мобильную ширину и возврат к исходному письму. В офлайн-задаче браузер запрещён, визуальный и production smoke не выполнялись.
