# Контракт восстановления Orchestra

## Область действия

Контракт задаёт требования для изолированной непроизводственной очереди `chat-v2`. Базовая ветка — `release/cycle3-final-rc`, базовый SHA — `27f62efcb8381e34f3de895c9fc41d1613c9cfd0`. Разрешённый файл — `docs/orchestra-recovery-contract-ru.md`; профиль проверки — `docs`.

## Состояние и намерение

- Долговечное состояние задачи должно храниться вне сессии Codex и переживать её завершение или перезапуск. Оно включает идентификатор задачи и транзакции, владельца, фазу, намерение, ожидаемые эффекты и ссылки на независимо подтверждённые результаты.
- Перед отправкой задания агенту или любой записью контроллер обязан надёжно сохранить намерение и идентификатор операции. Потеря ответа не отменяет сохранённое намерение.
- Самоотчёт агента не является доказательством успеха. Завершение подтверждается независимой проверкой фактического состояния и результатов.

## Восстановление и сверка

- После тайм-аута, перезапуска или потери ответа контроллер обязан независимо сверить состояние до любой повторной попытки. Допускается не более двух ограниченных чтений для сверки одной прерванной операции; каждое чтение имеет заранее заданные область и срок выполнения.
- Сверка должна установить, выполнена ли сохранённая операция, не выполнена ли она либо остаётся неоднозначной. Повтор допустим только при подтверждённом отсутствии выполнения и исключении продолжающегося исполнения прежним владельцем.
- Запрещены повторное исполнение и дублирование ветки, коммита, Draft PR или комментария транзакции. Найденный результат связывается с исходным намерением, а не создаётся заново.
- Неоднозначное прерванное исполнение сохраняет состояние `requires_reconciliation` и блокирует `NEXT`. Исчерпание двух чтений не даёт права предполагать успех или повторять операцию.

## Безопасный блокер и переход NEXT

- Безопасно установленный блокер допускает только изменение меток issue и публикацию одного комментария с фиксированным кодом причины (`reason_code`) из заранее заданного набора. Повторное обнаружение того же блокера не создаёт второй комментарий. Git-объекты при этом не создаются.
- Эти внешние действия выполняет только доверенный контроллер. Исполнитель возвращает структурированный результат `completed` или `blocked` и сам не публикует комментарии или другие объекты GitHub.
- Следующая задача выбирается автоматически только после внешнего подтверждения предшествующей транзакции публикации и освобождения её владельца. Неразрешённое состояние `requires_reconciliation` запрещает такой переход.

## Условия приёмки

Должен существовать только запрошенный новый файл в Markdown и UTF-8 с русским текстом; HEAD и база checkout должны остаться неизменными, а `git diff --check` — пройти без ошибок. Это требования приёмки, а не утверждение о результатах выполненных проверок. Доверенный контроллер независимо проверяет результат и публикует ровно один Draft PR и один комментарий транзакции.

## Явные шлюзы merge / deploy / root

- **Merge:** слияние требует отдельного явного разрешения доверенного контроллера после независимой проверки; эта задача такого разрешения не даёт.
- **Deploy:** развёртывание и доступ к production требуют отдельного явного разрешения; в рамках этой задачи они запрещены.
- **Root:** изменение установленного root-сервиса, системных служб или производственных endpoint требует отдельного явного разрешения; в рамках этой задачи оно запрещено. Восстановление не расширяет разрешённые пути или права доступа.
