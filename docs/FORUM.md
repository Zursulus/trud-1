# Временный форум и вход жителей по почте

Production-релиз 16.10.2026 включает **только форум для существующих учёток**:
`TRUD_FORUM_ENABLED=1`, `TRUD_RESIDENT_EMAIL_LOGIN_ENABLED=0`,
`TRUD_FORUM_PUBLIC_READ=0`. Точные команды: [RELEASE-20261016.md](RELEASE-20261016.md).
Регистрация и вход по коду ниже описывают отдельную выключенную возможность;
не включать её в этом релизе. Без ранее подтверждённого email доступно чтение,
но запись в форум остаётся запрещённой. Публичную статику в этом выпуске не публиковать.

Форум: `/admin/cabinet/forum/`. Регистрация и вход:
`/admin/cabinet/accounts/login/` → код в письме; новый житель выбирает
«Зарегистрироваться». Пароль и участок не нужны. Регистрация подтверждается
кодом за 10 минут, повторный вход — за 3 минуты; не более 3 попыток.
Используется штатный django-allauth 65.18.0 и стандартный Django EMAIL_BACKEND.
Существующий User с единственным email получает доступ той же учётной записью.
Совпадающие без учёта регистра адреса разных пользователей требуют ручного
разбора правлением: автоматически учётные записи не объединяются.

## Включение и выключение

В production оба флага по умолчанию выключены; при DEBUG включены:

```
TRUD_RESIDENT_EMAIL_LOGIN_ENABLED=1
TRUD_FORUM_ENABLED=1
TRUD_FORUM_PUBLIC_READ=0
TRUD_FORUM_MESSAGES_PER_MINUTE=3
```

Перед выпуском: проверенная резервная копия БД, установка зависимостей из
`backend/requirements.txt` в окружение выпуска, `manage.py migrate`,
`manage.py setup_roles`, `manage.py collectstatic --noinput` и перезапуск.
Миграции только добавляют таблицы forum/allauth; модели воды и жителей не меняются.
Сначала проверить выпуск на тестовом стенде, затем включать флаги решением владельца.
Для писем задать стандартные EMAIL_BACKEND, EMAIL_HOST, EMAIL_PORT,
EMAIL_USE_TLS/EMAIL_USE_SSL, DEFAULT_FROM_EMAIL и при необходимости SMTP credentials
в закрытом окружении службы. Для локальной проверки можно использовать
`EMAIL_BACKEND=django.core.mail.backends.console.EmailBackend`.

Выключение: оба флага в `0`, перезапуск. Новые URL вернут 404, ссылки исчезнут
(на публичной главной после обновления JSON, кеш до 60 секунд). Таблицы и история
сохраняются. Откат к предыдущему коду совместим с добавленными таблицами;
обратные миграции и удаление данных для отключения не нужны.
Уже открытые сессии жителей сохраняются, права кабинета остаются прежними.
Публичная главная статическая: отдельно опубликовать изменённые `index.html` и
`app.js` и `style.css`; Django отдаёт видимость ссылки через `/admin/public/content/`.
Форум использует существующий proxy `/admin/`, очередь — `/work/`.

## Правила и управление

Разделы создаёт «Администратор ТСН» в admin → «Разделы форума».
Чтение по умолчанию только после входа; запись — с подтверждённым текущим email.
Для старой сессии с паролем сначала выйти и войти по коду, чтобы подтвердить email.
Старый парольный вход жителей сохранён как совместимый запасной путь.
Вход сотрудников `/admin/` и `/work/`, Axes и существующая политика 2FA сохранены.
Служебные аккаунты и суперпользователи через allauth войти не могут;
почтовый backend не добавляет вход по email/паролю к старым формам.

Ник задаётся отдельно через «Мой ник»; иначе виден «Житель N».
ФИО, email, username и участок автоматически не показываются.
Темы/ответы — обычный экранированный текст до 5000 символов, заголовок до 160;
без загрузки вложений и изображений. Общий лимит тем и ответов на пользователя
за минуту проверяется по БД с блокировкой пользователя; на PostgreSQL между workers.
Автор правит своё 15 минут, пока тема открыта, текст и тема не скрыты.

`setup_roles` выдаёт группе «Администратор ТСН» право `forum.moderate_forum`;
его можно отдельно выдать другому пользователю. Модерация доступна в теме:
закрепить/открепить, закрыть/открыть, скрыть с обязательной причиной, вернуть.
Скрытое видят только модераторы. Записи не удаляются; темы и ответы сохраняют
simple_history, автора изменения и причину скрытия.
«Пожаловаться» → `/work/forum/`, доступ через штатный staff gate и право модерации.
Очередь позволяет перейти к сообщению и отметить жалобу проверенной.
Одна открытая жалоба от жителя на сообщение, не более 5 жалоб в минуту.

## Проверка владельцем перед включением

- Доставка письма, новая регистрация, старый житель, неверный/просроченный/повторный код.
- Сотрудник по-прежнему входит паролем через служебную форму и своим 2FA.
- Без участка форум работает, кабинет предлагает штатное «Запросить доступ».
- Создание раздела, темы, ответа; ник, переносы строк, правка, закрытие и скрытие.
- Жалоба попадает в рабочую очередь; обычный житель скрытое не видит.
- На телефоне 360–390 px читаются тема и форма, длинный текст не расширяет экран.

Автотесты (из backend):

```
DJANGO_DEBUG=1 DJANGO_TEST_SQLITE=1 DJANGO_SECRET_KEY=x TRUD_APPEAL_MALWARE_SCAN_REQUIRED=0 python manage.py test water config public_site forum
```

Также `manage.py check` и `manage.py makemigrations --check --dry-run`
с теми же переменными. SQLite не проверяет PostgreSQL row locks.
В рамках офлайн CLI выполнены серверные проверки HTML/CSS для мобильной ширины;
визуальная проверка на телефоне перед выпуском остаётся обязательной.
