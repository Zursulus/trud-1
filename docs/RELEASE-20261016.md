- Исходники баннера #80, редактор объявлений, картинок, контактов, закреплённых
  новостей и предпросмотр в рабочей базе.
- Форум, история тем/ответов, жалобы и модерация; кнопка «Обсуждения» в кабинете,

- Новая зависимость: только `django-allauth==65.18.0`.

Режим: `TRUD_FORUM_ENABLED=1`, `TRUD_RESIDENT_EMAIL_LOGIN_ENABLED=0`,
`TRUD_FORUM_PUBLIC_READ=0`. Анонимный запрос форума перенаправляется на прежний
вход в кабинет. Вошедшие существующие сотрудники и жители могут читать форум.
Новый вход по email и регистрация отключены: ссылки скрыты, GET/POST маршрутов
возвращают 404. Вход жителей по логину/паролю и служебный вход сохраняются.
Существующие приглашения/процедуры выдачи доступа владельцем не отключаются:
решение запрещает новую самостоятельную регистрацию через email.

Для записи в форум по текущей модели нужна **ранее подтверждённая** запись
`account.EmailAddress`. Миграции не подтверждают email существующим пользователям.
При выключенном email-входе пользователи без такого подтверждения читают форум,
но не создают темы/ответы/жалобы; не включать email-вход ради обхода этого правила.
Первый форум может быть пустым: миграция не создаёт разделы или пользователей.

**Публичные файлы `/var/www/trud-1/releases/<sha>` и Nginx не изменяются.**
Новые исходники главной не публикуются этим выпуском; новый баннер и новые блоки
главной доступны в предпросмотре редактора и потребуют отдельной публикации
статики. Backend API новостей/документов обновляется, существующие публикации
продолжают отдаваться. Обычный `collectstatic` обновляет Django-ресурсы `/static/`,
а не отдельную статическую главную.

root-only `service-status.txt` и `service-journal.txt` внутри release backup.
Если откат сам завершился ошибкой, сообщение «Откат не подтверждён» требует
ручного восстановления. После фиксации target поздняя ошибка даёт **exit 3**,
`COMMITTED_POSTCHECK_FAILED`: target остаётся установленным, откат не заявляется.
При SIGKILL/сбое питания автоматический откат не гарантирован.

## Что произойдёт с 2FA

Superuser и обе административные группы обязаны подтвердить OTP при доступе
к `/admin/` и `/work/`, включая ранее открытую password-only сессию.
Без подтверждённого устройства пользователь после пароля попадёт в настройку
2FA (`/admin/account/two_factor/setup/`), а не потеряет возможность её настроить.
При существующем устройстве нужна проверка OTP; наличие записи устройства само
по себе сессию не подтверждает. Потерянное устройство требует штатного recovery
из `docs/MFA.md`. Устройства/секреты/резервные коды релиз не меняет.
У сотрудников других групп и жителей нет нового принудительного enrollment;
существующий OTP-вход сотрудников остаётся доступным. Доступ к чужим участкам
или служебным данным форум не выдаёт.

## Восстановление БД — только при повреждении данных миграцией

Не восстанавливать БД ради ошибки HTTP, OTP, scanner или кода. Восстановление
заменяет рабочие данные и теряет записи после снимка. Не запускать обратные
миграции allauth/forum/public_site для обычного отката.

Если подтверждено повреждение: остановить приложение, исключить writers, сохранить
отдельную страховочную копию текущей БД/private-data, выбрать снимок и выполнить
процедуру `ops/RECOVERY.md`. У штатного backup сначала проверить `SHA256SUMS`,
`manifest.txt` (`restore_test=passed`), расшифровать при `encryption=age`, проверить
`pg_restore --list`; затем под блокировкой восстановить через
`pg_restore --clean --if-exists --exit-on-error` в `trud_site` от postgres.
При восстановлении снимка до миграций новые таблицы нужно отдельно учесть:
`--clean` чистит только объекты самого дампа, поэтому надёжный полный откат схемы —
восстановление в заново созданную пустую БД с прежним владельцем/правами по
согласованной процедуре восстановления. Не выдавать restore в непустую БД за
полное удаление новых таблиц. Документы восстанавливаются из **того же** снимка;
прежний каталог private-data сохраняется до завершения проверки. Код/marker вернуть
на baseline, выполнить `check`, запустить сервис и повторить smoke.

Свежий release dump проверен только `pg_restore --list`; его полный restore-test
перед восстановлением выполнить в изолированной БД. Не подменять им автоматически
ранее проверенную штатную копию. Ни один из вариантов не выполняется автоматически.
