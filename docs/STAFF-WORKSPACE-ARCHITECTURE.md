# Staff Workspace Architecture v1

Статус: проектный гейт перед реализацией `/work/`.

Цель: отделить ежедневную работу сотрудников ТСН от технического Django Admin, не переписывая существующую бизнес-логику, модель данных, права и аудит.

## 1. Принципы

1. `/work/` — прикладной интерфейс ежедневной работы.
2. `/admin/` — технический fallback для редких/служебных операций.
3. Бизнес-правила не дублируются между `/work/` и `/admin/`: оба слоя должны вызывать общие service/use-case функции.
4. Интерфейс строится вокруг рабочих задач и состояний, а не вокруг Django-моделей.
5. Mobile-first для полевых и оперативных действий; desktop-first для массовых операций, таблиц и сверки.
6. Fail closed: интерфейс не должен сам расширять права пользователя.
7. Никаких новых ролей без реального пользователя и отдельного процесса. Финансовые функции v1 остаются capability роли «Администратор ТСН».
8. Персональные данные не становятся частью обычного workspace только ради удобства; закрытый реестр остаётся отдельной границей.
9. Production не используется для отладки. Любой slice проходит branch/PR/tests/CI/smoke/deploy gate.
10. Не делать SPA и микросервисы без необходимости. Целевая архитектура v1: Django + PostgreSQL + server-rendered UI + точечный progressive enhancement.

## 2. Подтверждённые роли

### 2.1 Администратор ТСН

Основные задачи:
- вести рабочие лицевые счета и участки без доступа к закрытым ПД;
- проверять и исправлять рабочие данные с обязательной причиной;
- модерировать показания;
- работать с начислениями, оплатами, документами кабинета;
- обрабатывать обращения и запросы доступа в пределах выданных прав;
- публиковать новости и публичные документы;
- видеть общий журнал действий в read-only режиме.

### 2.2 Оператор воды

Основные задачи:
- вводить новые показания;
- работать с рабочим реестром счётчиков/групп без ПД;
- видеть контекст, необходимый для корректного ввода;
- не исправлять уже сохранённые значения;
- не работать с финансами и закрытым реестром.

### 2.3 Контролёр воды / старший линии

Основные задачи:
- видеть только закреплённые линии и участки;
- вносить показания по своей зоне;
- видеть предварительную разницу/контрольный контекст;
- не видеть чужие линии, финансы и закрытые ПД.

### 2.4 Закрытый реестр членов ТСН

Основные задачи:
- устанавливать связь `№ пользователя ↔ Person`;
- работать с Person / PlotRelation / PII-строками импорта;
- сверять legacy-контакты;
- не получать автоматически водные или финансовые write-права.

### 2.5 Технический администратор

Основные задачи:
- пользователи, группы, MFA, recovery;
- технические справочники;
- Django Admin;
- редкие аварийные операции;
- не является основной ежедневной пользовательской ролью.

## 3. Jobs To Be Done

### Администратор ТСН

1. «Когда приходит новый рабочий день, я хочу сразу увидеть всё, что требует решения, чтобы ничего не искать по десяткам таблиц.»
2. «Когда мне называют участок, номер счёта или номер обращения, я хочу за несколько секунд открыть правильный объект и его контекст.»
3. «Когда есть неоднозначное показание, обращение, доступ или начисление, я хочу увидеть причину, историю и безопасное следующее действие.»
4. «Когда исправляю рабочие данные, я хочу понимать последствия и оставить причину, чтобы изменение было проверяемым.»
5. «Когда работаю с финансами, я хочу видеть состояние счёта и операции как рабочий процесс, а не набор технических таблиц.»

### Оператор/контролёр воды

1. «Хочу быстро открыть свой рабочий список и внести показания без поиска по всей базе.»
2. «Хочу сразу увидеть предыдущее значение и подозрительную разницу до сохранения.»
3. «Хочу понимать, что принято, что пропущено и что требует повторного ввода.»

### Закрытый реестр

1. «Хочу найти № пользователя и безопасно сопоставить его с человеком/участком, не открывая лишние рабочие подсистемы.»
2. «Хочу видеть источник и историю соответствия, чтобы не создавать ложную идентичность.»

## 4. Информационная архитектура `/work/`

Основные уровни:

### 4.1 Рабочий стол

Назначение: ответить на вопрос «что требует моего действия сейчас?».

Блоки:
- Требует внимания;
- Последние события;
- Быстрые действия;
- Краткое состояние системы/данных;
- роль пользователя и его scope.

Примеры очередей:
- показания на проверке;
- новые обращения;
- запросы доступа;
- строки импорта на ручной разбор;
- начисления/оплаты, требующие проверки;
- ошибки бизнес-аудита.

Не показывать показатели, которые не ведут к действию, как главный элемент экрана.

### 4.2 Глобальный поиск

Один поиск по разрешённым текущей роли данным.

Минимальные ключи:
- номер участка / адрес;
- номер лицевого счёта;
- внутренний номер пользователя;
- номер счётчика;
- номер обращения;
- ФИО/телефон — только роли закрытого реестра;
- другие идентификаторы — только если они уже являются достоверными полями данных.

Результат поиска показывает тип объекта, главный идентификатор и безопасный контекст. Результаты не должны раскрывать данные, на которые нет permission.

### 4.3 Участки / лицевые счета

Список → карточка объекта → связанные процессы.

Карточка рабочего объекта должна собирать:
- идентификаторы участка/счёта;
- статус/архивность;
- водный контекст;
- финансовый контекст при наличии права;
- доступы/кабинет в разрешённом объёме;
- обращения;
- документы;
- историю рабочих изменений.

Person и закрытые ПД не подмешиваются автоматически.

### 4.4 Вода

Рабочие сценарии:
- внести показание;
- показания на проверке;
- журнал показаний;
- счётчики;
- линии/группы/узлы;
- водный баланс;
- ошибки/аномалии.

Жизненный цикл:
`ввод → предварительная проверка → moderation/review → утверждённое показание → история/баланс`.

### 4.5 Финансы

Рабочие сценарии:
- расчётный период;
- черновики начислений;
- проверка/утверждение;
- оплаты;
- распределение оплат;
- задолженность;
- выписка по счёту;
- корректировки.

Жизненный цикл:
`основание/правило → расчёт → draft → review → approved → payment → allocation → balance/history`.

Технические сущности BillingPolicy/PaymentAllocation и т.п. не обязаны называться так в пользовательском интерфейсе.

### 4.6 Обращения

Рабочие состояния:
- новые;
- в работе;
- ждём жителя;
- решённые/закрытые.

Карточка обращения:
- номер;
- участок/счёт;
- категория;
- тема;
- история диалога;
- вложения;
- текущий статус;
- разрешённые действия;
- время ожидания/последнее событие.

### 4.7 Доступ

Рабочие сценарии:
- запросы доступа;
- подтверждение основания;
- выдача/отзыв PortalGrant;
- приглашения;
- восстановление пароля;
- состояние кабинета.

Решение о доступе не должно обходить общий permission resolver.

### 4.8 Документы и публичный контент

Разделить:
- публичные новости;
- публичные документы;
- документы лицевого счёта;
- служебные материалы.

### 4.9 Опросы / правление

Отдельный процесс, не смешанный с основной карточкой участка:
- подготовка;
- проведение;
- результаты;
- протокол/аудит.

### 4.10 Служебное

Ссылка на `/admin/` и редкие операции.

Обычный пользователь `/work/` не должен видеть полный Django `app_list`.

## 5. Навигация

### Mobile

Базовая нижняя навигация v1:
- Главная;
- Работа;
- Поиск;
- Участки;
- Ещё.

`Ещё` содержит процессы, которые не являются постоянной нижней вкладкой: Вода, Финансы, Обращения, Доступ, Документы, Опросы, Служебное.

Контролёру воды допустима роль-адаптированная навигация: его стартовый экран может сразу вести в «Мои линии / Внести показание».

### Desktop

- постоянный sidebar;
- поиск всегда доступен;
- рабочие очереди в центральной области;
- таблицы поддерживают фильтры, сортировку, pagination и массовые действия только там, где они безопасны;
- нельзя копировать мобильные карточки 1:1 на широкий экран.

## 6. UI states, обязательные для каждого экрана

Каждый новый экран проектируется минимум для состояний:
- loading / переход;
- normal;
- empty;
- no permission;
- validation error;
- conflict / concurrent change;
- archived/inactive object;
- partial/incomplete data;
- system failure;
- success confirmation.

Ошибки должны объяснять следующее безопасное действие, а не только техническую причину.

## 7. Permission model UI

UI никогда не является источником права.

Правила:
1. backend permission/capability check обязателен на каждом действии;
2. `/work/` скрывает недоступные функции, но сервер всё равно проверяет доступ;
3. закрытый реестр остаётся отдельным capability boundary;
4. role-adapted dashboard строится из фактических permissions;
5. объектные scope-права контролёра применяются до выборки/выдачи данных;
6. изменение прав/доступа должно попадать в аудит;
7. legacy ResidentAccess мигрирует постепенно; новый UI не должен закреплять legacy как целевую модель.

## 8. Граница `/work/` и `/admin/`

### `/work/`

Ежедневно:
- поиск;
- просмотр объекта;
- рабочие очереди;
- ввод/проверка;
- обращения;
- финансы;
- документы;
- access workflow;
- пользовательские отчёты.

### `/admin/`

Редко:
- технические справочники;
- superuser operations;
- управление группами/пользователями;
- диагностика;
- аварийное редактирование;
- low-level historical/model inspection;
- временные инструменты миграции, пока они нужны.

Цель: обычная смена сотрудника не должна требовать захода в Django model changelist.

## 9. Application layer

До переноса крупных workflow в `/work/` бизнес-действия должны иметь единые функции/use-cases.

Приоритетные кандидаты:
- submit reading;
- moderate/approve/reject reading;
- calculate billing period;
- approve/cancel charge;
- allocate payment;
- issue/revoke portal access;
- approve/reject access request;
- answer/transition appeal;
- publish content;
- apply import row.

ModelAdmin и `/work/` должны быть адаптерами над этим слоем, а не двумя независимыми реализациями.

## 10. Первый vertical slice

Первый slice: **Глобальный поиск → рабочая карточка участка/лицевого счёта**.

Почему он первый:
- проверяет новую навигацию;
- проверяет permission filtering;
- создаёт основу почти для всех остальных процессов;
- сразу даёт практическую пользу;
- не требует переписывать финансовый или водный движок;
- позволяет проверить mobile + desktop дизайн-систему.

### 10.1 Scope v1

Маршруты, концептуально:
- `/work/` — минимальный shell/dashboard;
- `/work/search/`;
- `/work/accounts/`;
- `/work/accounts/<id>/`.

Карточка счёта/участка показывает только уже достоверные данные и разрешённые разделы.

Минимальные блоки:
- номер счёта / участок;
- архивность/статус;
- линии/группы/счётчики;
- последнее подтверждённое показание;
- финансовый balance summary при permission;
- открытые обращения при permission;
- документы при permission;
- доступ к кабинету в допустимом объёме;
- ссылки на существующие рабочие workflow;
- история последних изменений без ПД.

### 10.2 Не входит в первый slice

- редактирование Person;
- изменение закрытого реестра;
- полный финансовый workflow;
- массовый импорт;
- redesign resident portal;
- удаление старого Django Admin;
- новые роли;
- изменение схемы БД без отдельной необходимости.

## 11. Acceptance criteria первого slice

### Functional

1. Администратор ТСН открывает `/work/` и может перейти в глобальный поиск.
2. Поиск находит рабочий счёт/участок по номеру счёта и адресу.
3. Результат открывает единую карточку объекта.
4. Карточка показывает только разрешённые текущей роли данные.
5. Оператор воды не видит финансовые блоки и ПД.
6. Контролёр не может получить объект вне собственного scope через прямой URL.
7. Пользователь закрытого реестра не получает автоматически финансовые/водные write-действия.
8. Архивный объект визуально и функционально отличается от активного.
9. Ссылки на существующие water/finance/appeal workflow ведут в корректный контекст.
10. Django Admin продолжает работать как fallback.

### UX

1. iPhone viewport 390×844: нет горизонтального overflow.
2. Основное действие доступно без точного попадания в мелкие ссылки.
3. Поиск → карточка объекта выполняется максимум за 3 пользовательских действия после входа.
4. Desktop использует пространство экрана и не выглядит растянутой мобильной колонкой.
5. Empty/no-access/error состояния имеют понятный текст и следующий шаг.
6. В интерфейсе нет названий технических моделей, если они не нужны пользователю.

### Security/privacy

1. Нет расширения существующих permissions.
2. PII не появляется в ответах для обычного Администратора ТСН/оператора.
3. Object scope тестируется прямым URL, а не только скрытием ссылки.
4. CSRF/session/MFA baseline сохраняется.
5. Все write-действия (если появятся в slice) используют существующий audit/history contract.

### Quality

1. Django unit/integration tests.
2. PostgreSQL CI.
3. Playwright Chromium desktop + mobile.
4. Playwright WebKit critical smoke для `/work/`, поиска и карточки.
5. axe serious/critical gate.
6. Query budget для поиска и карточки, без N+1 на типичном наборе связанных объектов.
7. Regression test: `/admin/` остаётся доступным соответствующим ролям.

### Release

1. Отдельная Linear-задача.
2. Отдельная branch/PR.
3. Зелёный CI до merge.
4. До production: deployed SHA, clean tree, backup, compatibility gate.
5. После deploy: service/marker + HTTP smoke + физическая проверка на iPhone и desktop.
6. Результат и выявленные follow-up задачи фиксируются в Linear.

## 12. Design system v1

Не строить отдельную сложную библиотеку до первого slice. Зафиксировать минимальные примитивы:
- page shell;
- top bar;
- bottom navigation/mobile and sidebar/desktop;
- search field;
- action list;
- summary card;
- status badge;
- tab/segmented control;
- data table;
- form field;
- confirmation/error banner;
- empty state;
- destructive/privileged action pattern.

Семантика цветов:
- основной — нейтральный/brand;
- зелёный — подтверждено/нормально;
- жёлтый/amber — требует внимания;
- красный — ошибка/опасное действие;
- цвет не является единственным носителем смысла.

## 13. Нефункциональные требования

### Performance
- поисковый ответ и карточка не должны выполнять N+1 queries;
- отдельный query budget test;
- индексы добавлять только по измеренному запросу/плану.

### Accessibility
- keyboard/focus;
- semantic headings/labels;
- touch targets;
- WebKit/Chromium critical flows;
- axe serious/critical blocking.

### Observability
До масштабирования `/work/` должны быть наблюдаемы минимум:
- HTTP availability;
- 5xx rate;
- latency;
- disk usage;
- backup age/status;
- deployment SHA.

### Capacity
Production root disk >85% считается operational warning и должен быть разобран до активного наращивания функций.

## 14. Архитектурные non-goals v1

Не делать сейчас:
- frontend SPA;
- отдельный REST API только ради нового UI;
- microservices;
- переписывание PostgreSQL schema без продуктовой причины;
- big-bang рефакторинг `water`;
- удаление Django Admin;
- объединение Person/Account/LandPlot/User в одну сущность;
- автоматическое расширение роли из факта собственности/членства;
- редизайн всего продукта одним PR.

## 15. Порядок реализации после утверждения Architecture Pack

1. Operational gate: диск/retention/alerts.
2. `/work/` shell + role-adapted navigation.
3. Global search.
4. Account/plot work card.
5. WebKit + accessibility + performance gates.
6. Production smoke первого slice.
7. Затем отдельными vertical slices:
   - Water;
   - Appeals;
   - Finance;
   - Access;
   - Documents/content;
   - Governance/polls.
8. После стабилизации — постепенное вынесение бизнес-операций из ModelAdmin в application layer и уборка legacy-файлов.

## 16. Открытые решения перед первым кодовым PR

Нужно утвердить только четыре решения:
1. публичный URL staff workspace: `/work/` или `/staff/`;
2. название в UI: «Рабочая база», «Рабочее место» или другое;
3. какая сущность является основной карточкой первого slice: Account (лицевой счёт) с LandPlot-контекстом или LandPlot с Account-контекстом — решение по фактическим данным, не по названию;
4. считать ли обработку обращений частью первой волны сразу после карточки участка или после Water.

Остальное можно уточнять уже итеративно без повторного архитектурного проектирования.
