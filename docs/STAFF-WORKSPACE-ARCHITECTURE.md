# Staff Workspace Architecture v1

Статус: утверждённый архитектурный гейт для реализации `/work/`.

Цель: отделить ежедневную работу сотрудников ТСН от технического Django Admin, не переписывая существующую бизнес-логику, модель данных, права и аудит.

## 1. Утверждённые решения v1

1. URL рабочего интерфейса сотрудников: `/work/`.
2. Название в UI: «Рабочая база».
3. Технический центр первой рабочей карточки: `Account` (лицевой счёт) с контекстом `LandPlot`; пользователю карточка называется «Участок / лицевой счёт».
4. Порядок первых vertical slices: поиск + карточка → Water → Appeals → Finance → Access → Documents/content → Governance/polls.
5. Django Admin `/admin/` остаётся техническим fallback, но не является целевым ежедневным интерфейсом.
6. Архитектура v1: Django + PostgreSQL + server-rendered UI + точечный progressive enhancement. SPA, новый REST API только ради UI и микросервисы не нужны.
7. Новые роли не вводятся без реального пользователя и отдельного процесса. Финансы v1 остаются capability роли «Администратор ТСН».

## 2. Базовые принципы

- `/work/` строится вокруг задач и состояний, а не Django-моделей.
- Бизнес-правила не дублируются между `/work/` и `/admin/`: оба слоя используют общий application/service layer.
- UI никогда не является источником права: backend проверяет permission/capability и object scope на каждом действии.
- Персональные данные не подмешиваются в обычный workspace ради удобства; закрытый реестр остаётся отдельной границей.
- Mobile-first для оперативных/полевых действий; desktop использует таблицы, фильтры и массовые операции там, где они безопасны.
- Production не используется для отладки. Каждый slice проходит branch → PR → tests/CI → smoke → controlled deploy → production verification.

## 3. Подтверждённые роли

### Администратор ТСН

Ежедневно работает с рабочими лицевыми счетами и участками, показаниями, начислениями, оплатами, документами, обращениями, запросами доступа и публичным контентом в пределах выданных permissions. Закрытые ПД не получает автоматически.

### Оператор воды

Вводит новые показания и работает с необходимым водным контекстом без ПД и финансов. Не исправляет сохранённые значения без отдельного права.

### Контролёр воды / старший линии

Видит только закреплённые линии и участки, вносит показания по своему scope и не получает чужие линии, финансы или закрытые ПД.

### Закрытый реестр членов ТСН

Работает со связью `№ пользователя ↔ Person`, `Person`, `PlotRelation` и PII-строками импорта. Эта роль не получает автоматически водные или финансовые write-права.

### Технический администратор

Управляет пользователями, группами, MFA/recovery и редкими техническими операциями через Django Admin. Это не основная ежедневная роль.

## 4. Jobs To Be Done

### Администратор ТСН

- Сразу видеть, что требует решения сегодня.
- За несколько секунд находить участок, лицевой счёт, счётчик или обращение.
- Видеть контекст, историю и безопасное следующее действие при неоднозначной ситуации.
- Исправлять рабочие данные с понятными последствиями и обязательной причиной.
- Работать с финансами и обращениями как с процессами, а не набором технических таблиц.

### Оператор / контролёр воды

- Открыть свой рабочий список без поиска по всей базе.
- Перед вводом видеть предыдущее значение и подозрительную разницу.
- Понимать, что принято, пропущено или требует повторного ввода.

### Закрытый реестр

- Найти № пользователя и безопасно сопоставить его с человеком/участком.
- Видеть источник и историю соответствия, не создавая ложную идентичность.

## 5. Информационная архитектура `/work/`

### 5.1 Рабочий стол

Первый вопрос экрана: «что требует моего действия сейчас?».

Очереди могут включать:
- показания на проверке;
- новые обращения;
- запросы доступа;
- строки импорта на ручной разбор;
- начисления/оплаты, требующие проверки;
- ошибки бизнес-аудита.

Дополнительно: последние события, быстрые действия, роль и scope пользователя. Статистика без действия не должна занимать главный экран.

### 5.2 Глобальный поиск

Поиск выполняется только по данным, разрешённым текущей роли.

Минимальные ключи:
- номер/адрес участка;
- номер лицевого счёта;
- внутренний номер пользователя;
- номер счётчика;
- номер обращения;
- ФИО/телефон — только для закрытого реестра.

Результат показывает тип объекта, главный идентификатор и минимальный безопасный контекст без утечки данных.

### 5.3 Участок / лицевой счёт

Рабочая карточка собирает разрешённые сведения вокруг `Account`:
- номер лицевого счёта и участок;
- активность/архивность;
- линии, группы и счётчики;
- последнее подтверждённое показание;
- финансовый summary при permission;
- открытые обращения при permission;
- документы при permission;
- состояние доступа к кабинету в разрешённом объёме;
- последние рабочие изменения без ПД;
- переходы в существующие специализированные workflow.

`Person` и закрытые ПД автоматически не добавляются.

### 5.4 Вода

Жизненный цикл:
`ввод → предварительная проверка → review/moderation → утверждённое показание → история/баланс`.

Рабочие экраны: внести показание, проверка, журнал, счётчики, линии/группы/узлы, баланс, ошибки/аномалии.

### 5.5 Обращения

Состояния:
`новое → в работе → ждём жителя → решено/закрыто`.

Карточка содержит номер, участок/счёт, категорию, тему, историю диалога, вложения, статус, время последнего события и разрешённые действия.

### 5.6 Финансы

Жизненный цикл:
`основание/правило → расчёт → draft → review → approved → payment → allocation → balance/history`.

Пользовательские названия не обязаны повторять имена моделей `BillingPolicy`, `PaymentAllocation` и т.п.

### 5.7 Доступ

Процессы: запрос → проверка основания → выдача/отзыв `PortalGrant` → приглашение/восстановление → состояние кабинета. Решение не обходит общий permission resolver.

### 5.8 Документы и контент

Разделяются публичные новости, публичные документы, документы лицевого счёта и служебные материалы.

### 5.9 Опросы / правление

Отдельный workflow: подготовка → проведение → результаты → протокол/аудит.

### 5.10 Служебное

Ссылка на `/admin/` и редкие операции. Полный Django `app_list` не является частью обычного `/work/`.

## 6. Навигация

### Mobile

Нижняя навигация v1:
- Главная;
- Работа;
- Поиск;
- Участки;
- Ещё.

В «Ещё»: Вода, Финансы, Обращения, Доступ, Документы, Опросы, Служебное. Для контролёра стартовый сценарий может быть role-adapted: «Мои линии / Внести показание».

### Desktop

Постоянный sidebar, всегда доступный поиск, рабочие очереди в центральной области; таблицы получают фильтры, сортировку, pagination и безопасные массовые действия. Desktop не копирует мобильную колонку 1:1.

## 7. Обязательные UI states

Каждый новый экран проектируется для состояний:
- normal;
- empty;
- no permission;
- validation error;
- concurrent conflict;
- archived/inactive;
- partial/incomplete data;
- system failure;
- success confirmation.

Для server-rendered v1 отдельный искусственный loading-state не требуется, если нет асинхронной операции. Ошибка должна объяснять безопасное следующее действие.

## 8. Permission boundary

1. Backend permission/capability check обязателен на каждом действии.
2. Скрытие кнопки не заменяет server-side проверку.
3. Object scope контролёра применяется до выдачи объекта и проверяется прямым URL.
4. Закрытый реестр остаётся отдельным capability boundary.
5. Role-adapted dashboard строится из фактических permissions.
6. Изменения доступа аудитируются.
7. Legacy `ResidentAccess` мигрирует постепенно; новый UI не закрепляет его как целевую модель.

## 9. Граница `/work/` ↔ `/admin/`

### `/work/`: ежедневная работа

Поиск, рабочие очереди, карточки объектов, ввод/проверка, обращения, финансы, документы, access workflow и пользовательские отчёты.

### `/admin/`: технический fallback

Технические справочники, superuser operations, пользователи/группы, диагностика, аварийное редактирование, low-level history/model inspection и временные migration tools.

Целевое состояние: обычная смена сотрудника не требует использования Django model changelist.

## 10. Application layer

При переносе workflow в `/work/` бизнес-действия должны иметь общие use-case/service функции. Приоритетные кандидаты:
- submit reading;
- moderate/approve/reject reading;
- calculate billing period;
- approve/cancel charge;
- allocate payment;
- issue/revoke portal access;
- approve/reject access request;
- answer/transition appeal;
- publish content;
- apply import row.

`ModelAdmin` и `/work/` — адаптеры над этим слоем, а не независимые реализации правил.

## 11. Первый vertical slice

Первый slice: **`/work/` shell → глобальный поиск → рабочая карточка «Участок / лицевой счёт»**.

Концептуальные маршруты:
- `/work/`;
- `/work/search/`;
- `/work/accounts/`;
- `/work/accounts/<id>/`.

### Не входит

- редактирование `Person`;
- изменение закрытого реестра;
- полный финансовый workflow;
- массовый импорт;
- redesign resident portal;
- удаление Django Admin;
- новые роли;
- изменение схемы БД без продуктовой необходимости.

## 12. Acceptance criteria первого slice

### Functional

1. Администратор ТСН открывает `/work/` и попадает в «Рабочую базу».
2. Поиск находит рабочий счёт/участок по номеру счёта и адресу.
3. Результат открывает единую карточку объекта.
4. Карточка показывает только разрешённые текущей роли данные.
5. Оператор воды не видит финансовые блоки и ПД.
6. Контролёр не получает объект вне собственного scope через прямой URL.
7. Пользователь закрытого реестра не получает автоматически финансовые/водные write-действия.
8. Архивный объект явно отличается от активного.
9. Переходы в существующие water/finance/appeal workflows сохраняют корректный контекст.
10. Django Admin продолжает работать как fallback.

### UX

1. На viewport 390×844 нет горизонтального overflow.
2. Touch targets не требуют точного попадания в мелкие ссылки.
3. После входа поиск → карточка выполняется максимум за 3 действия.
4. Desktop использует пространство экрана, а не растягивает мобильную колонку.
5. Empty/no-access/error states содержат понятный следующий шаг.
6. Технические имена моделей не показываются без пользовательской необходимости.

### Security / privacy

1. Существующие permissions не расширяются.
2. PII не появляется для обычного Администратора ТСН, оператора или контролёра.
3. Scope проверяется server-side и прямым URL.
4. CSRF/session/MFA baseline сохраняется.
5. Любые write-действия используют существующий audit/history contract.

### Quality

1. Django unit/integration tests на PostgreSQL.
2. Playwright Chromium desktop + mobile.
3. Playwright WebKit critical smoke для `/work/`, поиска и карточки.
4. axe serious/critical gate.
5. Query budget для поиска и карточки; N+1 не допускается.
6. Regression: `/admin/` остаётся доступным соответствующим ролям.

### Release

1. Отдельная задача/трек разработки.
2. Отдельная branch/PR.
3. Зелёный CI до merge.
4. Перед production: deployed SHA, clean tree, backup, compatibility gate.
5. После deploy: service/marker, HTTP smoke и физическая проверка на iPhone и desktop.
6. Результат и follow-ups фиксируются в каноническом трекере.

## 13. Design system v1

Минимальные примитивы первого slice:
- page shell;
- top bar;
- mobile bottom navigation / desktop sidebar;
- search field;
- action list;
- summary card;
- status badge;
- tabs/segmented control;
- data table;
- form field;
- confirmation/error banner;
- empty state;
- privileged/destructive action pattern.

Цвет не является единственным носителем смысла. Красный используется только для ошибки/опасного действия, warning — для требующего внимания состояния, зелёный — для подтверждённого нормального состояния.

## 14. Нефункциональные требования

### Performance

Поиск и карточка имеют query-budget tests. Индексы добавляются по измеренному запросу/плану, а не заранее.

### Accessibility

Keyboard/focus, semantic headings/labels, touch targets, Chromium/WebKit critical flows, axe serious/critical blocking.

### Observability

До масштабирования `/work/` должны быть наблюдаемы минимум: HTTP availability, 5xx rate, latency, disk usage, backup age/status и deployment SHA.

### Capacity

Production root disk >85% — operational warning. 27.09.2026 первопричина текущего превышения была найдена в воспроизводимых RDC/npm/Puppeteer caches; после безопасной очистки использование снизилось с 87% до 71%. Retention/alerts остаются отдельным эксплуатационным улучшением.

## 15. Non-goals v1

Не делать сейчас:
- frontend SPA;
- отдельный REST API только ради нового UI;
- microservices;
- big-bang рефакторинг `water`;
- объединение `Person` / `Account` / `LandPlot` / `User`;
- автоматическое расширение роли из факта собственности/членства;
- удаление Django Admin;
- редизайн всего продукта одним PR.

## 16. Порядок реализации

1. Operational gate: непосредственный риск диска снят; retention/alerts ведутся отдельно.
2. `/work/` shell + role-adapted navigation.
3. Global search.
4. Account/LandPlot work card.
5. WebKit + accessibility + performance gates.
6. Production smoke первого slice.
7. Следующие отдельные slices: Water → Appeals → Finance → Access → Documents/content → Governance/polls.
8. После стабилизации — постепенный перенос business operations из `ModelAdmin` в application layer и уборка legacy-файлов.

Остальные детали уточняются итеративно внутри этих границ без повторного архитектурного проектирования.
