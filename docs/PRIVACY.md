# Труд-1: граница персональных данных

Цель архитектуры — не «уйти от 152-ФЗ», а минимизировать объём персональных данных в рабочей части сайта и число мест, где по данным можно определить конкретного человека.

## 1. Рабочая база личного кабинета

Основной человеческий идентификатор — `№ пользователя` (`ResidentNumberSlot.number`). Он не равен техническим `User.id`, `Account.id` или номеру участка.

Рабочий слой может хранить и использовать:

- № пользователя;
- лицевой счёт и участок;
- начисления и оплаты;
- счётчики и показания;
- обращения и ответы;
- закрытые документы конкретного лицевого счёта;
- технические статусы и события доступа.

В рабочем слое не следует дублировать ФИО, паспортные данные, дату рождения, СНИЛС/ИНН и другие идентификаторы человека.

## 2. Закрытый реестр членов ТСН

Связка `№ пользователя ↔ Person` хранится отдельно в `MemberRegistryEntry`.

Полные сведения о человеке остаются в `Person`; права на участок и основания остаются в `PlotRelation`. Эти модели и строки импорта с ФИО/контактами доступны только пользователям с отдельным правом `water.access_private_registry`.

Штатная группа: `Закрытый реестр членов ТСН`. Она не назначается автоматически и не даёт права на финансы, воду или изменение рабочих данных. Для обычного администратора ТСН эта группа не нужна.

Тестовый №333 никогда не связывается с `Person`.

## 3. Авторизация

`User` — техническая учётная запись входа, а не карточка человека.

Для жителя достаточно логина, хэша пароля, сессий и при необходимости технического email/телефона для приглашения, восстановления или уведомлений. `first_name`/`last_name` в resident-учётках не являются источником идентичности и не должны использоваться для хранения ФИО.

Сотрудники остаются отдельным случаем: их персональные учётные записи в административной части нужны для аудита действий.

## 4. Публичный сайт

Публичная часть содержит только информацию, предназначенную для всех: новости, объявления и общие документы. Персональные сведения жителей и закрытые документы участков туда не публикуются.

## 5. Legacy-поля

В существующей схеме исторически есть:

- `Account.contact_name`;
- `Account.phone`;
- ФИО/телефон/email в `ImportRow`;
- возможные resident `User.first_name` / `User.last_name`.

ZUR-59 не удаляет и не переносит эти значения автоматически. Обычная рабочая админка перестаёт показывать `Account.contact_name/phone`; экспорт лицевых счетов исключает их. `ImportRow`, `Person` и `PlotRelation` закрываются отдельным правом.

Команда:

```bash
python backend/manage.py audit_privacy_boundary
```

показывает только агрегированные количества и никогда не печатает сами ФИО/телефоны/email. `--strict` можно использовать после проверяемой миграции, когда legacy-граница должна быть полностью очищена.

## 6. Дальнейшая миграция legacy PII

Удалять дубли можно только после сверки:

1. получить агрегированный аудит;
2. для каждой legacy-записи установить однозначную связь с `Person` и № пользователя;
3. неоднозначные случаи оставить на ручную проверку;
4. сделать резервную копию;
5. перенести только подтверждённые сведения в закрытый реестр;
6. повторно проверить рабочие сценарии;
7. лишь затем очищать подтверждённые дубли из рабочих полей отдельной задачей и отдельной миграцией.

Прямой SQL, массовое угадывание соответствий и удаление неразобранных данных запрещены.

## 7. Короткая схема

```text
Реальный человек
      │
      ▼
[закрытый реестр]
Person ↔ № пользователя ↔ права на участок
      │
      │ только № пользователя
      ▼
[рабочая база]
участок / счёт / вода / платежи / обращения / документы
      │
      ▼
[авторизация]
логин / хэш пароля / сессии / технический канал восстановления

Публичный сайт ── без персональных данных жителей
```
