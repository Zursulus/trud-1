# Пересчёт тарифа: проверка и выпуск

Выполнен только локальный CLI-прогон на синтетических данных. Сеть, production,
реальные счета/жители и личный кабинет не использовались. Скриншотов и браузерного
smoke нет: задание прямо запрещает браузер, управление экраном и скриншоты.
Перед выпуском необходим мобильный smoke формы, сравнения, фильтров и утверждения
на тестовом контуре. Не считать серверные тесты проверкой отображения в Chromium.

## Методика и данные

- `/admin/water/tariff-recalculation/`: неизменяемый снимок отдельной версии.
- Ставка хранится в версии пересчёта с датами и основанием; глобальные Tariff и
  назначения BillingPolicy не переписываются. Тариф должен покрывать весь период.
- `node_excel`: знаменатель каждого SupplyNode — `confirmed_known` соответствующего
  узла из `calculate_water_balance(starts, ends).nodes`, то есть подтверждённые
  объёмы линий (для источника `reported` — GroupConsumption за точный период),
  а не сумма индивидуальных показаний. Другие источники водного баланса,
  включая отдельно учтённый полив, учитываются самим `calculate_water_balance`.
  Формула: ставка узла = ставка ВК × вход ОСН / `confirmed_known`;
  ROUND_HALF_UP до копеек. Эталон: 109,34 × 489 / 386 = 138,52 ₽/м³
  («Узел без гидранта»), 109,34 × 471 / 354 = 145,48 ₽/м³ («Узел с гидрантом»).
  При нулевом знаменателе ставка отсутствует, узел и его счета требуют проверки.
- Для каждой WaterGroup создаётся только в памяти Tariff со ставкой узла.
  Новые суммы берутся из `calculate_period(period, preview=True, group_tariffs=...)`:
  тот же путь расчёта воды, потерь и округления по действующим BillingPolicy /
  BillingAssignment. Штатный приоритет индивидуального тарифа сохраняется.
  Политика `node_excel` не добавляет повторных потерь поверх уже рассчитанной
  ставки узла. Предпросмотр возвращает несохранённые Charge, не меняет Tariff,
  начисления, историю или статус периода; утверждение по-прежнему — корректировки.
  Отсутствие действующих правил начислений оставляет счёт на проверке.
- Никаких средних/нормативов при отсутствии показаний: ручная проверка, без новой
  суммы. Финансовые замечания и пропуски индивидуальных показаний не исключают
  подтверждённые объёмы линий из знаменателя. Если водный баланс неполон,
  используется именно его известная часть `confirmed_known`, без выдуманных объёмов.
- Альтернативные методы распределяют потери внутри линии штатными group_volume /
  loss_weights / rounded_amount. Расход потерь округляется как в старом расчёте.
- В «было» включены действующие утверждённые и черновые вода/норматив/потери и прежние корректировки
  пересчёта. Счета с ручной корректировкой требуют сверки; услуги/платежи не меняются.
- Утверждение добавляет Charge(kind=adjustment) на разницу через save()/full_clean(),
  сохраняет прежние утверждённые начисления, историю simple-history и admin LogEntry.
  Черновые начисления воды готовых счетов отменяются с историей; разница для
  проводки считается от утверждённой суммы, а в сравнении — от «было». Период
  не переоткрывается; закрытый период требует отдельной корректировки следующего
  периода. Нулевые разницы не создают лишних начислений.
- Изменение исходных версий данных, начислений, тарифов, правил или назначений
  требует нового предпросмотра. Черновики прежней методики нужно создать заново.
  После утверждения можно создать новую версию с другим тарифом: предыдущие
  корректировки входят в «было». Отмена черновика не создаёт Charge.
  После утверждения обычный calculate_period не создаёт повторные начисления:
  изменить результат можно только новой версией пересчёта.
- Файлы используют существующие закрытое хранилище и проверку вложений (формат,
  размер, активное содержимое, антивирус согласно настройкам), скачивание с правами.
- Новые права: view/add_tariffrecalculation, отдельно approve_tariffrecalculation;
  setup_roles и миграция выдают их только роли «Администратор ТСН». Superuser без
  групп видит первую карточку админки. Существующая политика MFA сохранена.

## Совместимость, backup и откат

1. До production: полный gate, PostgreSQL sandbox, мобильный smoke. Изменение
   схемы не выкатывать обычным релизом без миграций. Здесь production не менялся.
2. Перед миграциями сверить установленный SHA, остановить записи на время выпуска,
   сделать backup базы и private-data и проверить восстановление по ops/RECOVERY.md.
   Локального SQLite-прогона недостаточно для проверки PostgreSQL-блокировок.
3. Применить обычные миграции water 0035/0036, затем setup_roles. 0035 добавляет
   таблицы и nullable FK в Charge/его историю; существующие записи не меняются.
   0036 добавляет права существующему администратору; остальные роли не расширяет.
4. Безопасный откат кода: оставить добавленную схему и записи. Старый код продолжит
   учитывать утверждённые корректировки в итогах, но не предоставит новый экран.
   Не назначать node_excel в старом расчётчике: этот метод использует новый экран.
5. Обратная миграция 0036 отбирает добавленные права, 0035 удаляет снимки и FK.
   После реальных утверждений её НЕ выполнять: потеряется связь с основанием.
   Возврат финансового результата — новая версия пересчёта/корректировка с историей;
   полное восстановление backup возможно только согласованной recovery-процедурой.
