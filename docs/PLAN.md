# Труд-1: рабочий план

Юридическое наименование: ТСН «ТРУД-1». Локация: Орджоникидзе, Крым.

Этот файл — актуальный технический план. Оперативный статус задач хранится в Linear, фактически установленная версия — на production через `/admin/deployment-status/`. Исторические промежуточные планы не дублируются здесь: они остаются в Git history.

## Источники истины

1. Linear — задачи, приоритеты, NOW/NEXT, blockers.
2. GitHub — код, тесты, CI и техническая документация.
3. Production `trud-1.ru` — фактически установленная версия.
4. Drive / Library — исходные Excel и крупные артефакты.
5. Notion — долговременные решения и карта проекта.

Push в GitHub не равен deploy.

## Текущее состояние — 21 сентября 2026

Ядро первой рабочей версии реализовано и проверено на production:

- реестр участков, людей, связей и постоянных внутренних ID;
- счётчики, показания, история и аудит изменений;
- предварительный разбор и безопасный импорт пакета данных;
- роли сотрудников, MFA, мобильное рабочее место оператора/контролёра;
- личный кабинет жителя, приглашения, восстановление доступа, документы и обращения;
- начисления, оплаты, долги, корректировки и квитанции;
- премодерация показаний контролёра;
- упрощённая рабочая панель админки без удаления стандартной Django-admin функциональности;
- ежедневный проверяемый backup, recovery, совместимый deploy и rollback;
- CI с Django tests и e2e.

Ключевые завершённые Linear-задачи: ZUR-6, ZUR-7, ZUR-8, ZUR-9, ZUR-10, ZUR-12, ZUR-39, ZUR-40, ZUR-41.

## Текущая фаза

Следующий этап — ZUR-11: развитие публичной части и интеграций. Работу вести отдельными атомарными задачами, не смешивая несвязанные изменения в один PR.

### 1. Новости и публичные документы

- управление новостями из админки без правки кода;
- публикация документов с понятными категориями и датами;
- публичные страницы без утечки персональных/служебных данных;
- сохранение текущего оформления сайта;
- desktop/mobile regression + tests.

Это ближайшая реализационная задача.

### 2. Водный баланс и контроль потерь

- общий входной объём по общим/контрольным счётчикам;
- сумма подтверждённого индивидуального/группового расхода;
- разница и процент потерь за период;
- явное отображение неполных данных;
- никаких автоматических начислений или распределения потерь без утверждённого правила.

### 3. Банковский обмен

Начинать только после получения реального формата/образца ВТБ.

До этого не придумывать структуру выписки или правила сопоставления. После получения образца сначала сделать read-only parser/dry-run, затем правила сопоставления, и только после проверки — импорт подтверждённых платежей.

### 4. Интеграция с 1С

Проектировать после банковского обмена и фиксации фактического финансового процесса. Не строить интеграцию по предположениям.

## Постоянные инварианты данных

- Участок, человек, пользователь входа, членство и лицевой счёт — разные сущности.
- Внутренний ID `TRUD-PLOT-*` не является автоматически номером участка или банковским лицевым счётом.
- Исторические связи собственника/представителя не переписываются задним числом.
- Не придумывать отсутствующие показания, даты, участки и соответствия.
- Неоднозначные строки импорта сохранять для ручной проверки.
- Формульные итоги Excel не считать первичными данными.
- Поле «Оплата по показаниям» не считать подтверждённым платежом без отдельного источника.
- Групповые кубы и потери не распределять автоматически без утверждённого правила.
- Публичный GitHub не должен содержать реальные телефоны, персональные данные, банковские данные, секреты или backup.
- Production не использовать для отладки.

## Правило выпуска

Для каждого изменения:

1. отдельная Linear-задача;
2. отдельная branch/PR, если меняется код;
3. tests/CI до merge;
4. перед production — сверка текущего deployed SHA, чистого дерева и backup;
5. compatible deploy использовать только если нет изменений migrations/requirements/settings/служебных management-команд;
6. изменения схемы/зависимостей требуют отдельного reviewed deploy-плана;
7. после deploy — smoke-check, marker, сервисы и короткая ручная проверка сценария;
8. результат зафиксировать в Linear.

## Definition of Done для следующего этапа

Задача считается закрытой только когда:

- код и тесты в GitHub;
- CI зелёный;
- production обновлён отдельным подтверждённым действием;
- smoke-check пройден;
- пользовательский сценарий проверен;
- Linear отражает фактический результат и следующий шаг.
