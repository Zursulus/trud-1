# Труд-1: проверка и уточнённый план
Дата: 2026-09-13. Место: Орджоникидзе (Орджо), Крым — уточнение владельца.
Юридическое наименование и форма требуют устава/реквизитов; категория земли сама по себе их не определяет.

## Подтверждённое состояние
Пять файлов статического сайта в GitHub. Backend, база пользователей, админка и интеграция с 1С отсутствуют.
На сервере пользователя: Debian 12, Nginx, PostgreSQL и отдельный процесс бота. По предоставленному выводу HTTPS отдаёт страницу, тест продления сертификата успешен, таймер включён.
Прямой SSH из рабочей среды недоступен. Текущая веб-проверка инструментом не удалась. Проверка кода не равна повторной проверке сервера.
На iPhone Unicode-значки стали цветными emoji. Исправлены на SVG. Место исправлено во всех текстах.
Повреждение слова «записи» в терминальном выводе не воспроизводится в GitHub: исходник корректный.
Форма была похожа на рабочий вход: ввод отключён до backend. Исправлен сброс aria-label.
CSS имеет повторные блоки оформления: технический долг, объединить при переносе в шаблоны.
Сервер работает с фиксированным релизом: изменения main сами не попадают на сайт.
Схема отката, резервное копирование сайта, внешняя проверка HTTP-редиректа и www ещё не подтверждены.

## Ошибки предыдущего подхода
Неверная география; преждевременные выводы по организационной форме.
Недостаточно явная граница между формой и действующей авторизацией.
Правовые и инфраструктурные проверки стояли слишком поздно.
Роли были слишком широкими: редактор не должен видеть расчёты жителей.
Платежи нельзя считать задолженностью без согласованной модели бухгалтерских данных.
Автоматизация обновлений и восстановление не были включены в критерии готовности.

## Принятая архитектура для следующего этапа
Одно приложение Django с серверными шаблонами, встроенными механизмами пользователей, сессий и админки.
Отдельные БД и роль PostgreSQL, системный пользователь, виртуальное окружение и systemd-служба сайта.
Не использовать базу, секреты и окружение бота. Приложение слушает локальный адрес за Nginx.
Секреты и резервные копии не входят в публичный GitHub.
Версию зависимостей фиксировать при реализации по поддерживаемой ветке; не придумывать версии сейчас.
Собственный класс пользователя определить до первых миграций. Идентификатор входа независим от номера участка; телефон — проверяемый контакт, не доказательство права на участок.
Публичная регистрация пока выключена. Приглашения одноразовые и ограничены сроком, создание первого администратора локальной командой.
Сброс доступа — по подтверждённому каналу либо через администратора с проверкой личности; не считать SMS подключёнными без провайдера.
Для административного доступа предусмотреть второй фактор.
CSRF, защищённые session cookies, ограничение попыток входа и отдельная проверка полномочий на каждый объект обязательны; Django сам по себе не решает разграничение по участкам.

## Порядок и критерии готовности
1. Инфраструктура и данные. Уточнить физическую страну размещения сервера и резервных копий по договору провайдера, ресурсы RAM/CPU, действующие резервные копии. До этого разрабатывать на вымышленных данных. Проверить оператора, основания обработки, уведомление РКН/актуализацию и публичную политику; проверить журналы доступа уже работающего сайта.
2. Админка новостей. Черновик, предпросмотр, публикация, снятие с публикации; заголовок, анонс, текст, картинка, дата. Редактор управляет контентом без доступа к пользователям и финансам. Файлы проверяются по типу/размеру, HTML очищается. Готово: редактор публикует новость с телефона, посетитель видит только опубликованное.
3. Авторизация и пустой кабинет. Приглашение, вход, выход, смена и восстановление пароля, блокировка и отзыв сессий. Привязка пользователя к одному или нескольким участкам с подтверждением и возможностью отзыва. Готово: пользователь A не получает данные B через подмену URL, формы или API; редактор не повышает себе права.
4. 1С. Получить название конфигурации и обезличенный образец выгрузки, определить идентификаторы и источники начислений/оплат. Сначала предварительный просмотр ручного импорта с отчётом ошибок, затем автоматизация. Повтор файла не дублирует операции, суммы сверяются с 1С, есть откат импорта. Показывать время обновления, не рисовать выдуманный баланс.
5. Запуск. Резервное копирование БД и файлов, пробное восстановление, атомарное обновление и откат; проверка HTTPS/редиректов, доступов и журналов. Тестовая группа, затем подключение остальных. Реальные персональные данные только после выполнения условий этапа 1.

## Итог продукта
Публичный сайт с новостями и документами, админка для редактора, защищённый кабинет с собственными начислениями/платежами из 1С.
Квитанции и оплата — только после подтверждения реквизитов и схемы работы; эквайринг не входит в первый релиз.
Карта соседей, чат, голосования и публичные списки должников не входят в первый релиз.

## Правовая проверка: границы
Это рабочий перечень, не заключение о полном соответствии.
Проверить 152-ФЗ (ст. 6, 9, 18, 18.1, 19, 21, 22), применимые меры защиты (ПП 1119, приказ ФСТЭК 21).
Проверить применимость 217-ФЗ/норм ГК по документам организации; не выбирать режим только по названию ТСН.
До публикации документов — права на тексты/фото, персональные данные, подписи и банковские сведения физлиц; закрытый кабинет не разрешает раскрывать всё всем членам.
Для платёжного функционала отдельно оценить применимость 54-ФЗ и 161-ФЗ к выбранной схеме. Не утверждать, что ККТ нужна или не нужна без определения вида платежа.
Публичные журналы Nginx не исследованы; нельзя утверждать, что статический сайт вообще не обрабатывает персональные данные.
