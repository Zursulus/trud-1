# Труд-1: рабочая база

Отдельное приложение Django работает на production по `/admin/`. Корневая публичная страница обслуживается отдельно.
Регистрации и кабинета жителей пока нет.

## Что работает

- 305 пустых карточек с постоянными ID. Повтор команды не стирает данные и не создаёт дублей.
- Лицевой счёт для банка хранится отдельной строкой: допускаются ведущие нули; неизвестный номер остаётся пустым.
- Адрес, контактное ФИО и телефон в старой карточке. Контакт не считается автоматически собственником или членом ТСН.
- Отдельные люди, участки и связи собственника/представителя с датами действия. Смена собственника оформляется закрытием прежней связи и созданием новой, без переписывания истории.
- Общие узлы, группы/линии, состав групп с датами, индивидуальные/общие/контрольные счётчики и полив.
- Показания по датам и отдельно кубы группы за период, с указанием передавшего.
- История изменений, автор действий в админке, причина исправления. Удаление через админку выключено.
- Защита входа от перебора, CSRF, проверка прав Django, обнаружение устаревшей формы.
- CSV выбранных карточек доступен уполномоченному сотруднику из списка счетов.

## Локальная проверка без данных жителей

Python 3.11 или новее. Из корня репозитория:

```sh
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
export DJANGO_DEBUG=1 DJANGO_TEST_SQLITE=1
.venv/bin/python backend/manage.py migrate
.venv/bin/python backend/manage.py seed_accounts
.venv/bin/python backend/manage.py createsuperuser
.venv/bin/python backend/manage.py runserver 127.0.0.1:8000
```

Открыть `http://127.0.0.1:8000/admin/`. Пароль вводится интерактивно, встроенного пароля нет.
Тестовая SQLite используется только при двух явных переключателях; production по умолчанию требует PostgreSQL и секрет.
Для проверки:

```sh
DJANGO_DEBUG=1 DJANGO_TEST_SQLITE=1 .venv/bin/python backend/manage.py test water
```

## Ввод воды

1. В карточках заполнить известные сведения. Не присваивать ID автоматически номерам участков из Excel.
2. Создать общие узлы и линии. Основной источник расхода линии оставить «Пока не определён», если правило неизвестно.
3. При необходимости добавить участников группы с датами. Конечная дата не включается: переход возможен в тот же день.
4. Создать счётчик и внести первое показание. Его расход неизвестен. Второе показание даст разницу за интервал между датами, не автоматически за календарный месяц.
5. Кубы от старшего вносить в «Кубы от старших», например с 1 августа до 1 сентября (не включая). Это одна запись на группу, без распределения по людям.
6. Для исправления значения открыть запись, указать причину и сохранить. История показывает старое и новое значение и сотрудника.

Замена счётчика — новая карточка счётчика и новое начальное показание. Показания разных счётчиков не вычитаются.
Дату и значение можно исправить с указанием причины и проверкой последовательности. Счётчик сохранённого показания фиксирован; исправление ошибочной привязки/удаление ошибочного замера требуют отдельной процедуры. Не обходить запрет прямым SQL.

## Границы первой сборки

Нет расчёта долга, цены с потерями, суммарного водного баланса и банковского обмена. Метка источника линии пока не запускает расчёты.
Нет импорта Excel: сначала нужно сопоставить строки с карточками и участками; имеющийся файл нельзя считать реестром всех 305 участков.
История simple-history — история прикладных изменений, не защита от администратора базы и не финансовый журнал.
QuerySet.update/bulk_update и прямой SQL обходят проверки и историю: прикладные изменения выполняются через save().
Для API и будущего импорта использовать те же проверки и транзакции, указать автора и причину.
Доступ к отдельным участкам для жителей ещё не реализован. Права сотрудника Django распространяются на весь разрешённый раздел.

## Production и обновление

Приложение установлено на production. Push в GitHub сам по себе сервер не обновляет.

1. Отдельные пользователь ОС, роль и база PostgreSQL, окружение Python, служба и секреты вне публичного каталога.
2. Настроить переменные по `.env.example`, `DJANGO_DEBUG=0`, длинный случайный `DJANGO_SECRET_KEY`, точный домен и HTTPS origin.
3. Проверить миграции на PostgreSQL, выполнить `migrate`, `seed_accounts`, `createsuperuser`, `collectstatic --noinput`.
4. Gunicorn запускается из каталога backend и слушает только loopback:
   `gunicorn config.wsgi:application --bind 127.0.0.1:8001 --workers 1 --timeout 30`.
5. Nginx проксирует только `/admin/`, статику админки берёт из `STATIC_ROOT`; существующая публичная страница продолжает работать.
6. При `DJANGO_TRUST_PROXY=1` Nginx обязан перезаписывать `X-Real-IP` значением `$remote_addr`, `X-Forwarded-Proto` значением `$scheme`, передавать Host. Не выставлять Gunicorn в интернет.
7. Админка опубликована через HTTPS. До внесения реальных персональных данных завершить ранее запланированный второй фактор и проверить доступ с телефона.
8. Разовый зашифрованный снимок новой БД создан и восстановление дампа проверено. Добавить БД в регулярный автоматический backup. История находится в той же базе и копируется вместе с ней.
9. Выполнить `manage.py check --deploy`; проверить сайт, новую админку и существующего бота независимо.

Для восстановления доступа: `manage.py changepassword ИМЯ`; после блокировки Axes — `manage.py axes_reset_username ИМЯ` из окружения приложения.
Реальные данные и резервные копии не добавлять в GitHub. Не подставлять реквизиты бота вместо настроек сайта.

## Проверки перед выпуском

CI проверяет Python 3.11 и PostgreSQL 15, миграции и тесты. Локальная SQLite не проверяет блокировки PostgreSQL.
В текущих тестах: повторное создание карточек, сохранение правок, нули/пропуски, точные дробные кубы, дубли и убывающие показания, периоды групп, история, устаревшая запись, формы admin, доступ, CSRF и блокировка входа.
