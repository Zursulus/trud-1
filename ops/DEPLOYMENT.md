# Совместимые обновления и откат

`deploy-compatible.sh` — стандартный путь для выпусков без изменений схемы,
зависимостей и настроек сервера. Требуются два полных SHA: целевой и ожидаемый
установленный. Исходный SHA сверяется с Git и локальным маркером; рабочее дерево
должно быть чистым, целевой коммит — потомком исходного. Неотслеживаемые рабочие
файлы тоже блокируют установку (игнорируемые секреты и private-data не мешают).

Скрипт запрещает изменения миграций, requirements, settings, management-команд и
резервного копирования. Дополнительно `migrate --check` проверяет, что нет
неприменённых миграций; сама установка миграции не выполняет. Эти ограничения
не доказывают семантическую совместимость кода: перед выпуском нужны review и CI.
Для миграций или смены зависимостей нужен отдельный проверенный план, включая
совместимость старого кода с новой БД. Старый `deploy-water-workspace.sh` —
исторический установщик конкретного выпуска, не универсальная команда обновления.

## Команда администратора

Подставить полный SHA проверенного выпуска вместо `TARGET_FULL_SHA`, а в
`expected` — SHA из проверенного публичного `/admin/deployment-status/`.
Выполнять от root на сервере. Сам скрипт берётся из целевого коммита без смены
рабочего дерева. `fetch` только скачивает код; production меняет последний шаг.

```sh
(
  set -eu
  target=TARGET_FULL_SHA
  expected=ddbfdac3309ea6bc99eb6cab09c44580953d04a8
  runuser -u trudsite -- git -C /opt/trud-1-site fetch origin feature/water-admin
  runuser -u trudsite -- git -C /opt/trud-1-site merge-base --is-ancestor "$target" origin/feature/water-admin
  installer=$(mktemp /tmp/trud-deploy.XXXXXXXX)
  trap 'rm -f "$installer"' EXIT
  runuser -u trudsite -- git -C /opt/trud-1-site show "$target:ops/deploy-compatible.sh" > "$installer"
  bash "$installer" "$target" "$expected"
)
```

Проверка после обновления: главная HTTP 200, `/admin/` HTTP 302, вход в кабинет
HTTP 200, публичный маркер содержит целевой SHA. Скрипт выполняет эти проверки.
Ролевые сценарии, ввод показаний и работа с телефона проверяются отдельно.

## Что происходит при сбое

Общий lock исключает пересечение с ежедневным backup. Сервис останавливается
до копирования базы и private-data, чтобы их состояние согласовывалось для
записей через приложение. Прямые SQL-записи и сторонние задания нужно исключить
организационно. Дамп проверяется `pg_restore --list`; полноценная проверка
восстановления остаётся задачей ежедневного backup по [RECOVERY.md](RECOVERY.md).

До переключения версии сбой возобновляет прежний сервис. После переключения
автоматический откат останавливает сервис, возвращает прежний коммит,
пересобирает статику и атомарно возвращает прежний маркер с исходной датой.
Затем запускает сервис и проверяет HTTP. Зависимости, схема, роли и backup units
не изменяются, база из снимка автоматически не восстанавливается: это позволяет
сохранить записи, поступившие после запуска новой версии.

При ошибке самого отката сообщение явно говорит, что восстановление не
подтверждено; при ошибке возврата кода или статики сервис не запускается.
Администратор проверяет журнал `trud-1-site.service`, текущий SHA и каталог
`/var/backups/trud-compatible.*`, указанный в выводе. SIGINT/SIGTERM вызывают
откат; SIGKILL, отключение питания и отказ диска требуют ручного восстановления.
Для полного восстановления базы/файлов действует [RECOVERY.md](RECOVERY.md).
Предрелизные копии содержат закрытые данные, доступны root и автоматически не
удаляются; срок хранения и очистку определяет администратор.

## Проверки разработчика

```sh
python3 -m unittest discover -s ops/tests -v
bash -n ops/deploy-compatible.sh
```

Тесты запускают настоящий Bash без root, в изолированном временном каталоге.
Операции сервера заменены заглушками: проверяются отказ при расхождении версии,
грязном дереве и несовместимом выпуске, ошибки копирования, проверки приложения,
миграций, запуска, HTTP/маркера, прерывание и неудачный откат. Это проверка
управления установкой, не реальное восстановление PostgreSQL/systemd.
